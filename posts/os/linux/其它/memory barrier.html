memory barrier

以下所有示例伪代码中，如果内存地址前加上*号, 表示访问该内存地址处，在等号左边表示STORE操作，在等号右边表示LOAD操作。如果内存地址前没有*号，则仅仅表示该内存地址，通常为将该内存地址存储到某个指针变量中。如果指针变量前有两个**号，则为访问该指针变量指向的值。

THE THINGS CPUS GET UP TO(这句话要怎么翻译？只可意会吧，cpu执行指令时的一些七七八八)

假设我们的代码中有这么一段程序 a = A; B = b; c = C; d = D; E = e; 我们可能认为cpu在执行这段代码时，会按照我们程序代码中所写的顺序访问内存 LOAD A, STORE B, LOAD C, LOAD D, STORE E. 事实上不是这样

  • load操作通常是要立即完成的，加载完数据之后才能对加载的数据做后续的计算。而store操作，通常是可以defered
  • load也可以预加载，而预加载可能获取的数据并不是程序代码中所期望获取到的数据
  • 实际访存的顺序也会受到cpu buses和caches的影响，为了更好的使用cpu buses 和caches,访问的顺序可能会被reorder。比如在buses空闲时做预加载。而多cpu之间的 cache，虽然单次访存操作数据会最终一致，但多次访存读写顺序并不能保证一致(一个cpu的读写执行顺序，别的cpu作为观察者能观察到的执行顺序却是不同的)

所以这段代码在执行时，可能实际在该cpu上的执行顺序如下 LOAD A, LOAD {C,D}, STORE E, STORE B (Where "LOAD {C,*D}" is a combined load)

如果我们不考虑多cpu，只考虑单个cpu的情况，每个cpu不管如何乱序执行，它都需要保证程序中所体现出来的因果关系，比如如下程序中的一段代码 U = A; A = V; A = W; X = A; A = Y; Z = A; 不管实际是如何执行的，最终的结果都应该如下所示 U == the original value of A X == W Z == Y A == Y 这叫做单个cpu需要保证的self-consistent。 也就是说如果只有单个cpu，虽然它也会乱序执行程序中的指令，但都会保证程序本身的语义或者因果关系，我们是不需要做任何干预的。只有在多个cpu下访问相同的内存(共享数据），才会考虑使用memory order影响cpu的访存顺序。

除了cpu，编译器也会reorder程序指令，编译器可能会对一段读写内存的指令做combine,discard,defer。 比如： A = V; A = W; 会被优化成： A = W; 同样： A = Y; Z = A; 会被优化成： A = Y; Z = Y;

ABSTRACT MEMORY ACCESS MODEL

cpu memory module,或者memory order，指的是cpu所执行的指令在内存上生效的顺序。多个cpu不管它按照什么顺序执行访存指令，这些访存指令最终会交错在内存上生效，该顺序叫做memory order.

通常我们上层程序假设的cpu memory order/memory module是very relaxed,也就是说cpu在执行访存指令时，只要不违反程序指令中的因果关系，会任意做乱序访存。编译器也是如此，都只提供relaxed memory module。

比如我们有如下两个程序指令流

    CPU 1        CPU 2
    ===============    ===============
    { *A == 1; *B == 2 }
    *A = 3;        x = *A;
    *B = 4;        y = *B;

这两个cpu在实际执行指令时，不会保证每个cpu的这两条指令的先后循序，故在这4条访存指令到达内存时，所形成的memory order,会有4！种顺序，如下 STORE A=3, STORE B=4, x=LOAD A->3, y=LOAD B->4 STORE A=3, STORE B=4, y=LOAD B->4, x=LOAD A->3 STORE A=3, x=LOAD A->3, STORE B=4, y=LOAD B->4 STORE A=3, x=LOAD A->3, y=LOAD B->2, STORE B=4 STORE A=3, y=LOAD B->2, STORE B=4, x=LOAD A->3 STORE A=3, y=LOAD B->2, x=LOAD A->3, STORE B=4 STORE B=4, STORE A=3, x=LOAD A->3, y=LOAD B->4 STORE B=4, ... ... 所以最终x,y的结果也是`22=4`中情况 x == 1, y == 2 x == 1, y == 4 x == 3, y == 2 x == 3, y == 4

除了cpu本身的乱序执行外，一个cpu在执行两个store指令时，即使这两个store指令都按照先后的顺序committed to memory了，而另一个cpu在加载时，这个先后顺序却不能在加载中体现出来。这是由于cache的影响。也就是在某个时间点，后store的值在另一个cpu上可以读到，先store的值却读不到。 如下

    CPU 1        CPU 2
    ===============    ===============
    { *A == 1, *B == 2, *C == 3, *P == A, *Q == C }  #P,Q为指针变量
    *B = 4;        *Q = *P;
    *P = B        D = **Q;

cpu2上执行的指令有因果关系（data dependency)，因此只能按照指令中的顺序，先 STORE *Q=*P,再加载**Q.所以最后的结果中，一定不会出现D=3这种情况。 而对于cpu1而言，这两个STORE指令没有因果关系，是会乱序执行的。所以最终的结果有3种情况 (Q == A) and (D == 1) (Q == B) and (D == 2) (*Q == B) and (D == 4)

而如果我们保证cpu1的执行顺序，比如给两个STORE中间加个write barrier,则这两个store指令一定是先执行*B=4,再执行*P=B,这时候假设在cpu2上执行*Q = *P时，如果我们获取到的P已经指向了B,之后再获取*B,获取到的B处存储的值可能还是2，也就是*B=4这个更新却读不到的情况。这种情况怎么解决呢？在两次读操作之间加个read barrier/data dependent barrier，

GUARANTEES

不管cpu+编译器的 memory module 如何relax,有些情况下的顺序总是要保证的，也就是要保证程序的因果关系/data dependency 1) 在任意cpu上，dependent memory accesses will be issued in order.

如下 *Q = *P; D = **Q; cpu 执行这两个指令的memory order一定是 LOAD *P, STORE *Q ,LOAD **Q 也就是上段程序的语义，先将指针Q指向指针P的指向，再获取指针Q指向的值，这个语义是一定要保证的。也就是第二个load依赖于第一个load

2) Overlapping loads and stores within a particular CPU will appear to be ordered within that CPU.

a = X; X = b;//这两个读写访问同一个地址，overlapped了，memory order要保证一致 a = LOAD X, STORE X = b

X = c; d = X; //这两个读写访问同一个地址，overlapped了，memory order要保证一致 STORE X = c, d = LOAD X 虽然可以优化为 *X = c; d = c;// 省去了第二个LOAD指令

3) independent loads and stores 是不会保证任何顺序的

老生长谈了

4) overlapping memory accesses may be merged or discarded

X = A; Y = (A + 4);//这两个load指令访问的地址overlapping了，最终的memory order会有如下三种情况 X = LOAD A; Y = LOAD (A + 4); Y = LOAD (A + 4); X = LOAD A; {X, Y} = LOAD {A, (A + 4) }; 第三种情况是这两个加载指令被merged到一个load指令中执行了。(batch load)

如下指令， A = X; Y = A; 最终的memory order只会有两个情况，第二种是Load被discard. STORE A = X; Y = LOAD A; STORE *A = X; Y=X;

WHAT ARE MEMORY BARRIERS?

memory barrier就是使cpu/compiler在执行访存指令时，保证memory order。

VARIETIES OF MEMORY BARRIER

  • Write (or store) memory barriers. write memory barriers保证在barrier之前的所有store operations happen before 在barrier之后的所有store operation. write memory barrier 通常与read memory barrier 或者 data dependency barrier配对使用

  • Data dependency barriers. data dependency barriers只对interdependent loads起作用，interdependent loads是指第二个load依赖于第一个load,比如第一个load加载地址，第二个load再从该地址处加载值。这两个load本身就是有因果关系的，即使不使用data dependency barrier，其加载循序也是保证的。这里加上data dependency barrier确保在data dependency barrier之前的任意load,if that load touches one of a sequence of stores from another CPU, then by the time the barrier completes, the effects of all the stores prior to that touched by the load will be perceptible to any loads issued after the data dependency barrier.

    通常data dependency barrier需要与wirte barriers配对使用

  • Read (or load) memory barriers. read memory barrier是data dependency barrier plus a guarantee that all the LOAD operations specified before the barrier will appear to happen before all the LOAD operations specified after the barrier. read memory barrier包含data dependency barrier的保证，所以data dependency barrier也可以用read memory barrier替代。 但是read memory barrier比data dependency barrier多的功能是即使是independent loads也会保证顺序。 read memory barrier通常也与write memory barrier配对使用
  • General memory barriers. general memory barriers 确保在barrier之前的所有读写操作都happen before barrier之后的读写操作。 general memory barrier 既包括write memory barrier也包括read memory barrier的功能

Memory barriers are only required where there's a possibility of interaction between two CPUs or between a CPU and a device. If it can be guaranteed that there won't be any such interaction in any particular piece of code, then memory barriers are unnecessary in that piece of code.

DATA DEPENDENCY BARRIERS

这里给个需要使用data dependency barrier的例子，这个例子其实之前已经有了

    CPU 1        CPU 2
    ===============    ===============
    { A == 1, B == 2, C = 3, P == &A, Q == &C }
    B = 4;
    <write barrier>
    P = &B
            Q = P;
            D = *Q;

对于cpu2而言，这两个加载指令有明显的依赖关系，根据gurantee的第一条规则，cpu2执行这两个指令的memory order一定是与指令顺序一致的。那么结果就会是一下两种情况么? (Q == &A) implies (D == 1) (Q == &B) implies (D == 4) 并不是，还可能出现第三种情况(Q == &B) and (D == 2)，也就是说CPU 2's perception of P may be updated before its perception of B。虽然cpu1先执行B=4,再执行P=&B,而当cpu2在执行 Q=P时，即使看到P更新后的值，当再读取B时，B的更新竟然看不到。也就是对CPU2而言，B的更新在P之后。这是因为split cache的影响,比如在DEC Alpha cpu上，就可能出现这样情况。

为了解决这个问题，就需要给第二个cpu的load操作添加data dependency barrier 或者 read barrier

    CPU 1        CPU 2
    ===============    ===============
    { A == 1, B == 2, C = 3, P == &A, Q == &C }
    B = 4;
    <write barrier>
    P = &B
            Q = P;
            <data dependency barrier>
            D = *Q;

Note that this extremely counterintuitive situation arises most easily on machines with split caches, so that, for example, one cache bank processes even-numbered cache lines and the other bank processes odd-numbered cache lines. The pointer P might be stored in an odd-numbered cache line, and the variable B might be stored in an even-numbered cache line. Then, if the even-numbered bank of the reading CPU's cache is extremely busy while the odd-numbered bank is idle, one can see the new value of the pointer P (&B), but the old value of the variable B (2).

另一个使用data dependency barrier的例子如下，从内存中读取一个值作为访问数组的索引

    CPU 1        CPU 2
    ===============    ===============
    { M[0] == 1, M[1] == 2, M[3] = 3, P == 0, Q == 3 }
    M[1] = 4;
    <write barrier>
    P = 1
            Q = P;
            <data dependency barrier>
            D = M[Q];

READ BARRIERS

给个使用read barrier的例子，read barrier适用于两次load之间没有依赖关系。

    CPU 1            CPU 2
    =======================    =======================
        { A = 0, B = 9 }
    STORE A=1
    <write barrier>
    STORE B=2
                LOAD B
                LOAD A [first load of A]
                <read barrier>
                LOAD A [second load of A]

这里对cpu2而言，如果LOAD B读出来的值是2，第一个LOAD A读出来的值可能是0或者1，但是第二个读出来的值肯定会是1

SMP BARRIER PAIRING

A write barrier should always be paired with a data dependency barrier or read barrier, though a general barrier would also be viable. Similarly a read barrier or a data dependency barrier should always be paired with at least an write barrier, though, again, a general barrier is viable:

    CPU 1        CPU 2
    ===============    ===============
    a = 1;
    <write barrier>
    b = 2;        x = b;
            <read barrier>
            y = a;

or

    CPU 1        CPU 2
    ===============    ===============================
    a = 1;
    <write barrier>
    b = &a;        x = b;
            <data dependency barrier>
            y = *x;

Note that the stores before the write barrier would normally be expected to match the loads after the read barrier or the data dependency barrier, and vice versa:

    CPU 1                           CPU 2
    ===============                 ===============
    a = 1;           }----   --->{  v = c
    b = 2;           }    \ /    {  w = d
    <write barrier>        \        <read barrier>
    c = 3;           }    / \    {  x = a;
    d = 4;           }----   --->{  y = b;

LOAD SPECULATION（预加载）对memory order的影响

很多cpu会执行预加载，也就是cpu预测到需要从内存中加载某个item，并且当前的bus是空闲的，便会提前将该item加载到cpu，即使当前的执行流没有到加载的那条指令。等到到了要执行加载指令时，因为已经提前加载了，这个指令就会complete immediately.

It may turn out that the CPU didn't actually need the value - perhaps because a branch circumvented the load - in which case it can discard the value or just cache it for later use.

Consider:


    CPU 1               CPU 2
    =======================    =======================
                    LOAD B
                    DIVIDE        } Divide instructions generally
                    DIVIDE        } take a long time to perform
                    LOAD A

Which might appear as this:


                                            :       :       +-------+
                                            +-------+       |       |
                                        --->| B->2  |------>|       |
                                            +-------+       | CPU 2 |
                                            :       :DIVIDE |       |
                                            +-------+       |       |
    The CPU being busy doing a --->     --->| A->0  |~~~~   |       |
    division speculates on the              +-------+   ~   |       |
    LOAD of A                               :       :   ~   |       |
                                            :       :DIVIDE |       |
                                            :       :   ~   |       |
    Once the divisions are complete -->     :       :   ~-->|       |
    the CPU can then perform the            :       :       |       |
    LOAD with immediate effect              :       :       +-------+

Placing a read barrier just before the second load:

    CPU 1               CPU 2
    =======================    =======================
                    LOAD B
                    DIVIDE
                    DIVIDE
                <read barrier>
                    LOAD A

这会使得在真正之后最后的加载时，会对之前的预加载做依赖检查，If there was no change made to the speculated memory location, then the speculated value will just be used:


                                            :       :       +-------+
                                            +-------+       |       |
                                        --->| B->2  |------>|       |
                                            +-------+       | CPU 2 |
                                            :       :DIVIDE |       |
                                            +-------+       |       |
    The CPU being busy doing a --->     --->| A->0  |~~~~   |       |
    division speculates on the              +-------+   ~   |       |
    LOAD of A                               :       :   ~   |       |
                                            :       :DIVIDE |       |
                                            :       :   ~   |       |
                                            :       :   ~   |       |
                                        rrrrrrrrrrrrrrrr~   |       |
                                            :       :   ~   |       |
                                            :       :   ~-->|       |
                                            :       :       |       |
                                            :       :       +-------+

but if there was an update or an invalidation from another CPU , then the speculation will be cancelled and the value reloaded:

                                            :       :       +-------+
                                            +-------+       |       |
                                        --->| B->2  |------>|       |
                                            +-------+       | CPU 2 |
                                            :       :DIVIDE |       |
                                            +-------+       |       |
    The CPU being busy doing a --->     --->| A->0  |~~~~   |       |
    division speculates on the              +-------+   ~   |       |
    LOAD of A                               :       :   ~   |       |
                                            :       :DIVIDE |       |
                                            :       :   ~   |       |
                                            :       :   ~   |       |
                                        rrrrrrrrrrrrrrrrr   |       |
                                            +-------+       |       |
    The speculation is discarded --->   --->| A->1  |------>|       |
    and an updated value is                 +-------+       |       |
    retrieved                               :       :       +-------+

CACHE COHERENCY 对memory order的影响

之前有说过cache也是会影响cpu memory order reorder 的一个原因.这里看看具体会怎么影响。 for while the caches are expected to be coherent, there's no guarantee that that coherency will be ordered. This means that whilst changes made on one CPU will eventually become visible on all CPUs, there's no guarantee that they will become apparent in the same order on those other CPUs. Consider dealing with a system that has a pair of CPUs (1 & 2), each of which has a pair of parallel data caches (CPU 1 has A/B, and CPU 2 has C/D):

                :
                :                          +--------+
                :      +---------+         |        |
    +--------+  : +--->| Cache A |<------->|        |
    |        |  : |    +---------+         |        |
    |  CPU 1 |<---+                        |        |
    |        |  : |    +---------+         |        |
    +--------+  : +--->| Cache B |<------->|        |
                :      +---------+         |        |
                :                          | Memory |
                :      +---------+         | System |
    +--------+  : +--->| Cache C |<------->|        |
    |        |  : |    +---------+         |        |
    |  CPU 2 |<---+                        |        |
    |        |  : |    +---------+         |        |
    +--------+  : +--->| Cache D |<------->|        |
                :      +---------+         |        |
                :                          +--------+
                :

Imagine the system has the following properties:

  • an odd-numbered cache line may be in cache A, cache C or it may still be resident in memory;

  • an even-numbered cache line may be in cache B, cache D or it may still be resident in memory;

  • whilst the CPU core is interrogating one cache, the other cache may be making use of the bus to access the rest of the system - perhaps to displace a dirty cacheline or to do a speculative load;

  • each cache has a queue of operations that need to be applied to that cache to maintain coherency with the rest of the system;

  • the coherency queue is not flushed by normal loads to lines already present in the cache, even though the contents of the queue may potentially affect those loads.

Imagine, then, that two writes are made on the first CPU, with a write barrier between them to guarantee that they will appear to reach that CPU's caches in the requisite order:

    CPU 1        CPU 2        COMMENT
    ===============    ===============    =======================================
                    u == 0, v == 1 and p == &u, q == &u
    v = 2;
    smp_wmb();            Make sure change to v is visible before
                     change to p
    <A:modify v=2>            v is now in cache A exclusively
    p = &v;
    <B:modify p=&v>            p is now in cache B exclusively

now imagine that the second CPU wants to read those values:

    CPU 1        CPU 2        COMMENT
    ===============    ===============    =======================================
    ...
            q = p;
            x = *q;

The above pair of reads may then fail to happen in the expected order, as the cacheline holding p may get updated in one of the second CPU's caches whilst the update to the cacheline holding v is delayed in the other of the second CPU's caches

    CPU 1        CPU 2        COMMENT
    ===============    ===============    =======================================
                    u == 0, v == 1 and p == &u, q == &u
    v = 2;
    smp_wmb();
    <A:modify v=2>    <C:busy>
            <C:queue v=2>
    p = &v;        q = p;
            <D:request p>
    <B:modify p=&v>    <D:commit p=&v>
              <D:read p>
            x = *q;
            <C:read *q>    Reads from v before v updated in cache
            <C:unbusy>
            <C:commit v=2>

Basically, whilst both cachelines will be updated on CPU 2 eventually, there's no guarantee that, without intervention, the order of update will be the same as that committed on CPU 1.

To intervene, we need to interpolate a data dependency barrier or a read barrier between the loads. This will force the cache to commit its coherency queue before processing any further requests:

    CPU 1        CPU 2        COMMENT
    ===============    ===============    =======================================
                    u == 0, v == 1 and p == &u, q == &u
    v = 2;
    smp_wmb();
    <A:modify v=2>    <C:busy>
            <C:queue v=2>
    p = &v;        q = p;
            <D:request p>
    <B:modify p=&v>    <D:commit p=&v>
              <D:read p>
            smp_read_barrier_depends()
            <C:unbusy>
            <C:commit v=2>
            x = *q;
            <C:read *q>    Reads from v after v updated in cache

EXPLICIT KERNEL BARRIERS

The Linux kernel has a variety of different barriers that act at different levels:

(*) Compiler barrier.

(*) CPU memory barriers.

(*) MMIO write barrier.(memory mapped i/o write barrier)

  • COMPILER BARRIER The Linux kernel has an explicit compiler barrier function that prevents the compiler from moving the memory accesses either side of it to the other side: barrier(); 这个barrier对load和store指令都有效，是general barrier

  • CPU MEMORY BARRIERS The Linux kernel has eight basic CPU memory barriers:

    
  TYPE        MANDATORY        SMP CONDITIONAL
  ===============    =======================    ===========================
  GENERAL        mb()            smp_mb()
  WRITE        wmb()            smp_wmb()
  READ        rmb()            smp_rmb()
  DATA DEPENDENCY    read_barrier_depends()    smp_read_barrier_depends()

C++ Memory Order

typedef enum memory_order {
    memory_order_relaxed,
    memory_order_consume,
    memory_order_acquire,
    memory_order_release,
    memory_order_acq_rel,
    memory_order_seq_cst
} memory_order;

std::memory_order提供了可供选择的原子操作前后的内存序。原子操作默认的内存序是sequentially consistent ordering,也即是memory_order_seq_cst

  • memory_order_relaxed 不保证原子操作前后的内存序，只保证原子操作的原子性，比如如下的计数程序

    #include <vector>
#include <iostream>
#include <thread>
#include <atomic>

std::atomic<int> cnt = {0};

void f()
{
    for (int n = 0; n < 1000; ++n) {
        cnt.fetch_add(1, std::memory_order_relaxed);
    }
}

int main()
{
    std::vector<std::thread> v;
    for (int n = 0; n < 10; ++n) {
        v.emplace_back(f);
    }
    for (auto& t : v) {
        t.join();
    }
    std::cout << "Final counter value is " << cnt << '\n';
}

    Final counter value is 10000

  • memory_order_consume 这个其实现就是在load操作之后加上data dependency barrier。与write barrier配对使用。 如果线程A对某个原子变量atomic store的memory order是memory_order_release，也就是在该atomic store 前加上write barrier，另一个线程B对该原子变量的atomic load是 memory_order_consume，也就是在该原子变量的atomic load操作之后加上data dependency barrier，并且如果该load 读取到了线程A store的值，那么线程B中atomic load之后与该原子变量有data dependency的变量的读取，如果其store操作在线程A中在atomic store 之前完成，则最新值可以被读取。 这里就是使用data dependency barrier做同步的模型

    如下例所示，

    #include <thread>
#include <atomic>
#include <cassert>
#include <string>

std::atomic<std::string*> ptr;
int data;

void producer()
{
    std::string* p  = new std::string("Hello");
    data = 42;
    ptr.store(p, std::memory_order_release);
}

void consumer()
{
    std::string* p2;
    while (!(p2 = ptr.load(std::memory_order_consume)))
        ;
    assert(*p2 == "Hello"); // never fires: *p2 carries dependency from ptr
    assert(data == 42); // may or may not fire: data does not carry dependency from ptr
}

int main()
{
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join(); t2.join();
}

    其指令顺序的简化模型如下

        producer        consumer
    ===============    ===============

    store data=42 ;
    <write barrier>
    store ptr = p
            load ptr;
            <data dependency barrier>
            load data

    需要注意这个例子中,data 与 ptr 并没有data dependency关系，所以在consumer线程中，即使我们对ptr的load使用了memory_order_consume，也即是在load之后加上了data dependency barrier,并且我们读取到了producer store到ptr中的值， 也不能保证 producer 对data的更新在consumer中可见。

    这里需要使用 read barrier,也即是memory_order_acquire

  • memory_order_acquire 就是在load之后加上 read barrier, 跟store release 配合使用

    #include <thread>

    互斥锁的实现就是使用的原子变量和load acquire, store release memory order. 這裡需要保證一個線程unlock之前的所有store,在另一個線程lock之後可見，同時，需要保證一個線程的lock，和unlock之間的cirtical section不會被reorder到區域外。

    std::atomic<int> l;

void lock(){
     while (!l.compare_exchange_strong(0, 1, std::memory_order_acq_rel)) {
        schedule();//sleep on the sleep queue
        }
}

void unlock(){
    l.compare_exchange_strong(1, 0, std::memory_order_acq_rel)
    wake_up(); //wake up process on the queue
}

  前面说过，general barrier同时具有read barrier 和write barrier的功能

* memory_order_release
  没啥说的，就是在atomic store之前加上write barrier

* memory_order_acq_rel
  这个就是 atomic store之前加上 write barrier, 而atomic load之后加上read barrier.
  如果是RMW,则既加上了 read barrier，也加上了write barrier，即general barrier

  下例中，其结果可能R1 == R2 == 0，因为thread1 x.store的write barrier只能保证前后写操作顺序，y.load也只能保证前后读操作顺序，而这两个语句本身可能reorder,同理thread2的两个语句也会reorder，最后读出R1 == R2 == 0
  ```c++
  atomic<int> x; // = 0
  atomic<int> y; // = 0

  // thread 1
  x.store(1, memory_order_acq_rel);
  R1 = y.load(memory_order_acq_rel);

  // thread 2
  y.store(1, memory_order_acq_rel);
  R2 = x.load(memory_order_acq_rel);

  • memory_order_seq_cst Atomic operations tagged memory_order_seq_cst not only order memory the same way as release/acquire ordering (everything that happened-before a store in one thread becomes a visible side effect in the thread that did a load), but also establish a single total modification order of all atomic operations that are so tagged.

    acq_rel的memory order只在 load 和store访问的是同一个变量，并且load读取到store存储的值时，其store之前的存储和load之后的加载才能同步

    常用的使用模型如下

    int data; // = 0
atomic<int> flag; // = 0

// thread 1
data = produce_data(); // produce data
flag.store(1, memory_order_release); // notify consumer

// thread 2
if (flag.load(memory_order_acquire))
consume_data(data);

    如果不存在在两个线程中对同一个变量load和store的同步点，或者同步点前后不存在需要同步的操作，这时候怎么保证memory order呢，这时候只能使用seq_cst了。 seq_cst establish a single total modification order of all atomic operations

  #include <thread>
  #include <atomic>
  #include <cassert>

  std::atomic<bool> x = {false};
  std::atomic<bool> y = {false};
  std::atomic<int> z = {0};

  void write_x()
  {
      x.store(true, std::memory_order_seq_cst);
  }

  void write_y()
  {
      y.store(true, std::memory_order_seq_cst);
  }

  void read_x_then_y()
  {
      while (!x.load(std::memory_order_seq_cst))
          ;
      if (y.load(std::memory_order_seq_cst)) {
          ++z;
      }
  }

  void read_y_then_x()
  {
      while (!y.load(std::memory_order_seq_cst))
          ;
      if (x.load(std::memory_order_seq_cst)) {
          ++z;
      }
  }

  int main()
  {
      std::thread a(write_x);
      std::thread b(write_y);
      std::thread c(read_x_then_y);
      std::thread d(read_y_then_x);
      a.join(); b.join(); c.join(); d.join();
      assert(z.load() != 0);  // will never happen
  }

最后如果我们要保证z.load() != 0不等于0，只能使用std::memory_order_seq_cst，如果是std::memory_order_acq_rel，是无法满足的，因为x,y的store分别在两个不同的线程中，同步点前后并没有对上。

原子操作默认是std::memory_order_seq_cst，也就是默认即是最强的内存序。（sequential consistency ,顺序一致性）
