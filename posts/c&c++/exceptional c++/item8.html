item8

  • exception-safe： works properly in the presence of exceptions
  • exception-neutral：propagates all exceptions to the caller
template <class T> 
class Stack
{
public:
  Stack();
  ~Stack();
  Stack(const Stack&);
  Stack& operator=(const Stack&);
  size_t Count() const;
  void Push(const T&);
  T Pop(); // if empty, throws exception
private:
  T* v_; // ptr to a memory area big
  size_t vsize_; // enough for 'vsize_' T's
  size_t vused_; // # of T's actually in use
};

Make Stack exception-safe and exception-neutral. That is, Stack objects should always be in a correct and consistent state, regardless of any exceptions that might be thrown in the course of executing Stack's member functions. If any exceptions are thrown, they should be propagated seamlessly through to the caller, who can deal with them as he pleases, because he knows the context of T and we don't.

  • 首先是默认构造函数和析构函数，要求exception-safe and exception-neutral 
    template<class T>
Stack<T>::Stack()
: v_(new T[10]), // default allocation
vsize_(10),
vused_(0) // nothing used yet
{}
    new T[10]要么调用默认的 operator new[],要么调用T重载的operator new[]，然后调用10次T::T(),如果 operator new[] fail，会抛出 bad_alloc异常。如果 T::T() fail,异常被catch,那么已经创建的T对象会被析构，分配的内存会被通过operator delete[]释放 因此这个函数是exception-safe and exception-neutral 的

这里先不讨论 T的析构函数抛出异常的可能性。如果T的析构函数抛出异常了，which would call terminate() and simply kill the program altogether and leave events well out of your control anyway.

template<class T>
Stack<T>::~Stack()
{
delete[] v_; // this can't throw
}

delete[] 首先调用T::~T()十次，然后调用operator delete[]. c++标准要求 operator delete[] 不会抛出异常,其签名必须是

void operator delete[]( void* ) throw(); //noexcept
void operator delete[]( void*, size_t ) throw(); //noexcept

那么就剩下T::~T(),如果析构函数抛出异常，那么我们的Stack的析构函数不可能是exception safe的。这个稍微想下就知道不好处理。 因此，我们通常都会要求T的析构函数不得抛出异常

异常安全的规则之一： Never allow an exception to escape from a destructor or from an overloaded operator delete() oroperator delete[](); write every destructor and deallocation function as though it had an exception specification of "throw()".

  • 其次是拷贝构造和拷贝赋值函数，要求exception-safe and exception-neutral

我们首先实现一个helper函数NewCopy, NewCopy takes a pointer to (src) and size of(srcsize) an existing T buffer, and returns a pointer to a new and possibly larger copy of the buffer,passing ownership of the new buffer to the caller. If exceptions are encountered, NewCopy correctly releases all temporary resources and propagates the exception in such a way that nothing is leaked.

template<class T>
T* NewCopy( const T* src, size_t srcsize, size_t destsize )
{
  assert( destsize >= srcsize );
  T* dest = new T[destsize];
  try
  {
    copy( src, src+srcsize, dest );
  }
  catch(...)
  {
    delete[] dest; // this can't throw
    throw; // rethrow original exception
  }
  return dest;
}

首先是new T[destsize],这个之前已经分析过了，是exception-safe and exception-neutral 的，然后是copy,这会调用T::operator=(),如果抛出异常了，我们会调用delete[] dest，看起来是异常安全的，然而却要求 T::operator=() 在抛出异常时，被赋值的对象是可被析构的

//拷贝构造
template<class T>
Stack<T>::Stack( const Stack<T>& other )
: v_(NewCopy( other.v_, other.vsize_, other.vsize_ )),
vsize_(other.vsize_),
vused_(other.vused_){}

//拷贝赋值
template<class T>
Stack<T>&
Stack<T>::operator=( const Stack<T>& other )
{
  if( this != &other )
  {
    T* v_new = NewCopy( other.v_, other.vsize_, other.vsize_ );
    delete[] v_; // this can't throw
    v_ = v_new; // take ownership
    vsize_ = other.vsize_;
    vused_ = other.vused_;
  }
  return *this; // safe, no copy involved
}

异常安全的规则之二：In each function, take all the code that might emit an exception and do all that work safely off to the side. Only then, when you know that the real work has succeeded, should you modify the program state (and clean up) using only nonthrowing operations.

  • count()

    template<class T>
size_t Stack<T>::Count() const
{
  return vused_; // safe, builtins don't throw
}

  • push()

    template<class T>
void Stack<T>::Push( const T& t )
{
if( vused_ == vsize_ ) // grow if necessary
{ 
  // by some grow factor
  size_t vsize_new = vsize_*2+1;
  T* v_new = NewCopy( v_, vsize_, vsize_new );
  delete[] v_; // this can't throw
  v_ = v_new; // take ownership
  vsize_ = vsize_new;
}
v_[vused_] = t;
++vused_;
}

  • pop()

// Hmmm... how safe is it really?
template<class T>
T Stack<T>::Pop()
{
  if( vused_ == 0)
  {
    throw "pop from empty stack";
  }
  else
  {
    T result = v_[vused_-1];
    --vused_;
    return result;
  }
}

如果T result = v_[vused_-1];抛出异常，则stack的状态不会改变， 这看上去是exception safe的，但是如果我们考虑如下使用这个pop

string s1(s.Pop());

pop返回这个temporary object转而用于构造string对象，那么如果这个构造函数抛出异常了，这时候，我们pop出的对象就永远丢失了。这似乎不能是pop函数所控制的。

如果我们更改下pop函数的签名，

template<class T>
void Stack<T>::Pop( T& result )
{
  if( vused_ == 0)
  {
    throw "pop from empty stack";
   }
  else
  {
    result = v_[vused_-1];
    --vused_;
  }
}

This ensures that the Stack's state is not changed unless the copy safely arrives in the caller's hands.

实际上，pop这个函数在设计上有两个功能，1， pop出栈顶元素，2， 返回栈顶元素。事实上，这两个功能应该分开。

如果应该如下实现这两个功能

template<class T>
T& Stack<T>::Top()
{
  if( vused_ == 0)
  {
      throw "empty stack";
  }
  return v_[vused_-1];
}

template<class T>
void Stack<T>::Pop()
{
  if( vused_ == 0)
  {
      throw "pop from empty stack";
  }
  else
  {
      --vused_;
  }
}

事实上，标准库的pop*也是如此设计的，都是不返回pop出的元素，而提供访问top/front/back元素的接口

当我们说一个函数，或者一个对象的实现是exception safe的，这exception safe 保证了什么？

exception safe的保证有3类

  • Basic guarantee。 以容器为例，如果其操作抛出异常，容器不会泄露资源，同时还是可继续被操作的。
  • Strong guarantee。If an operation terminates because of an exception, program state will remain unchanged. This always implies commit-or-rollback semantics, including that no references or iterators into the container be invalidated if an operation fails. 显然，我们实现的stack不是Strong guarantee， push接口在没有空间时会先重新分配空间，然后调用T的赋值操作。如果赋值操作发生异常，stack的状态已经发生了改变，这时候，如果之前有访问top的引用，这个引用就也无效了。
  • Nothrow guarantee。 The function will not emit an exception under any circumstances。比如析构函数，swap

我们当前实现的stack的exception safe,需要T的类型提供以下接口或保证：

  • Default constructor
  • Copy constructor (if Pop returns by value)
  • Nonthrowing destructor (to be able to guarantee exception-safety)
  • Exception-safe copy assignment

优化

  • 我们可以专门实现一个用来管理内存的类,提高封装性
  • 异常安全的规则之三：使用RAII(resource acquisition is initialization,资源获取即初始化)规则来isolate resource ownership and management，提高封装性
//StackImpl is responsible for simple raw memory management and final cleanup, so any class that uses it won't have to worry about those details.
template <class T> 
class StackImpl
{
/*????*/:

  ~StackImpl();

  T* v_; // ptr to a memory area big

构造函数：

template <class T>
StackImpl<T>::StackImpl( size_t size )
: v_( static_cast<T*> ( size == 0 ? 0 : operator new(sizeof(T)*size) ) ),
vsize_(size),
vused_(0)
{}

注意我们调用的是operator new，而不是直接调用new

析构函数

template <class T>
StackImpl<T>::~StackImpl()
{
    destroy( v_, v_+vused_ ); // this can't throw
    operator delete( v_ );
}

swap

template <class T>
void StackImpl<T>::Swap(StackImpl& other) throw()
{
  swap( v_, other.v_ );
  swap( vsize_, other.vsize_ );
  swap( vused_, other.vused_ );
}

构造函数只需要调用StackImpl的构造函数即可。注意StatckImpl的构造函数并不会调用T的默认构造函数。

析构函数 我们不需要自己提供析构函数，编译器默认提供的析构函数足以，它会调用StackImpl的析构函数，析构buffer中的T object, 释放内存。

拷贝构造

Stack(const Stack& other): StackImpl<T>(other.vused_)
{
  while( vused_ < other.vused_ )
  {
    construct( v_+vused_, other.v_[vused_] );
    ++vused_;
  }
}

注意这里的construct只调用了T的拷贝构造函数，没有调用T::operator=().如果T的拷贝构造抛出异常，在栈展开时，编译器会调用基类，也就是StackImpl的析构函数，correctly destroy exactly as many objects as were successfully created,and then deallocate the raw memory.

这个版本的优化，因为在StackImpl中封装了资源的获取和释放，stack的构造和析构大大简化了，不管我们需要写多少其他的构造函数，都不需要在stack的构造函数中处理clean-up code。 同时，我们不需要写try/catch代码也可以写出exception-safe code

再以StackImpl 作为 Stack的member object为例，重新实现 Stack的函数

template <class T>
class Stack
{
public:
    Stack(size_t size=0): impl_(size)
    {}
    Stack(const Stack& other)
    : impl_(other.impl_.vused_)
    {
      while( impl_.vused_ < other.impl_.vused_ )
      {
        construct( impl_.v_+impl_.vused_, other.impl_.v_[impl_.vused_] );
        ++impl_.vused_;
      }
    }
    Stack& operator=(const Stack& other)
    {
      Stack temp(other);
      impl_.Swap(temp.impl_); // this can't throw
      return *this;
    }
    size_t Count() const
    {
        return impl_.vused_;
    }
    void Push( const T& t )
    {
      if( impl_.vused_ == impl_.vsize_ )
      {
        Stack temp( impl_.vsize_*2+1 );
        while( temp.Count() < impl_.vused_ )
        {
            temp.Push( impl_.v_[temp.Count()] );
        }
        temp.Push( t );
        impl_.Swap( temp.impl_ );
      }
      else
      {
        construct( impl_.v_+impl_.vused_, t );
        ++impl_.vused_;
      }
    }
    T& Top()
    {
      if( impl_.vused_ == 0 )
      {
        throw "empty stack";
      }
      return impl_.v_[impl_.vused_-1];
    }
    void Pop()
    {
      if( impl_.vused_ == 0 )
      {
        throw "pop from empty stack";
      }
      else
      {
        --impl_.vused_;
        destroy( impl_.v_+impl_.vused_ );
      }
    }
private:
    StackImpl<T> impl_; // private implementation
};

以上的两个实现，对T的要求只有2点

  • Copy constructor
  • Nonthrowing destructor

不需要赋值操作，本质上是因为 Stack的赋值操作的实现是copy and swap. 每次都会分配新的内存，释放原有的内存。这真的高效么？

异常安全规则总结 (1) Never allow an exception to escape from a destructor or from an overloaded operator delete() or operator delete; write every destructor and deallocation function as though it had an exception specification of "throw()." (2) Always use the "resource acquisition is initialization" idiom to isolate resource ownership and management. (3) In each function, take all the code that might emit an exception and do all that work safely off to the side. Only then, when you know that the real work has succeeded, should you modify the program state (and clean up) using only nonthrowing operations.

标准库的异常安全guarantee:

  • All standard containers must implement the basic exception safe guarantee for all operations
  • multi-element inserts ("iterator range" inserts) are never strongly exception-safe.
  • for vector and deque , inserts and erases (whether single- or multi-element)are only basic exception safe , not strongly exception safe
  • single insert and erase from other containers are strongly exception safe.

What does this mean for you? Well, if you write a class that has a container member and you perform range insertions, or you write a class that has a member of type vector or deque, and T's copy constructor or assignment operator can throw, then you are responsible for doing the extra work to ensure that your own class's state is predictable if exceptions do occur. Fortunately, this "extra work" is pretty simple. Whenever you want to insert into or erase from the container, first take a copy of the container, then perform the change on the copy. Finally, use swap to switch over to using that new version after you know that the copy-and-change steps have succeeded.
