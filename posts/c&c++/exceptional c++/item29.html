Compilation Firewalls

In C++, when anything in a class definition changes (even private members), all users of that class must be recompiled. To reduce these dependencies, a common technique is to use an opaque pointer to hide some of the implementation details.

class X
{
public:
/* ... public members ... */
protected:
/* ... protected members? ... */
private:
/* ... private members? ... */
struct XImpl;
XImpl* pimpl_; // opaque pointer to
// forward-declared class
};

One big advantage of this idiom is that it breaks compile-time dependencies. First, system builds run faster, because using a Pimpl can eliminate extra #includes as demonstrated previously. I have worked on projects in which converting just a few widely-visible classes to use Pimpls halved the system's build time. Second, it localizes the build impact of code changes because the parts of a class that reside in the Pimpl can be freely changed—that is, members can be freely added or removed—without recompiling client code.

那么 XImpl中应该放什么呢？有四种选择

  • Put all private data (but not functions) into XImpl.
  • Put all private members（data and non virtual functions） into XImpl.
  • Put all private and protected members into XImpl.
  • Make XImpl entirely the class that X would have been, and write X as only the public interface made up entirely of simple forwarding functions

如何评价这四种选择？

  • 这是最基本的，但仍可以进一步隔离
  • Put all nonvirtual private members into XImpl. 通常，做到这一步就可以了。需要注意的是，virtual function是不能放到pimpl的，不管这个virtual function是不是private的，是不是继承的。
  • 这是不对的
  • 这个实现可以避免在XImpl中存储指向X的back pointer， 如果说XImpl中存储的函数在执行时需要访问X的函数的话。 The chief drawback is that it usually makes the visible class useless for any inheritance as either a base or a derived class.

最好的实现是这样：在Put all nonvirtual private members into XImpl的基础上，如果XImpl中的函数需要调用X中的函数的话，将这些被调用的函数也放到XImpl中，避免还要在XImpl中存储指向X的指针

Guideline ：For widely used classes, prefer to use the compiler-firewall idiom (Pimpl Idiom) to hide implementation details. Use an opaque pointer(a pointer to a declared, but undefined, class) declared as "struct XxxxImpl; XxxxImpl* pimpl_;" to store private members .

那么以上的pimpl实现有哪些代价？

  • space overhead 首先需要的额外的指针，如果impl中需要存储back pointer的话，则是2个额外的指针。而总的空间的额外消耗还需要再加上padding的字节,以便pointer的地址能够对齐。在32位架构上pointer对齐到4的整数倍地址，64位对齐到8的整数倍。 当然，我们也可以使用 compiler-specific #pragmas 避免对齐。 Many compilers will let you override the default alignment/packing for a given class; see your vendor's documentation for details. if your platform only "prefers" (rather than "enforces") pointer alignment and your compiler offers this feature,you can avoid space for pointer alignment
  • performance overhead 首先是 XImpl对象的分配和释放，如果使用new operator，调用全局 ::operator new(), 最终调用的是malloc,malloc分配空间，首先有额外cookie的消耗，而且可能需要陷入内核分配堆空间。这是比较消耗资源的。

For another, each access of a member in the Pimpl can require at least one extra indirection; if the hidden member being accessed itself uses a back pointer to call a function in the visible class, there will be multiple indirections.

* 使用自由链表分配不同大小的内存块，这个实现是比较灵活的，比如自由链表初始时需不需要预分配内存块，在当前链表没有内存块的情况下，可不可以从其他链表借内存块，对并发的支持等等。gnu c++ 标准库代码中提供了__gnu_cxx::__pool_alloc就是用自由链表缓存的内存块

#include <ext/pool_allocator.h>
#include <iostream>

struct XImpl
{
    XImpl():c('a'),d(2){}

    static void* operator new( size_t size ){
        std::cout<<"using overload opeartor new"<<std::endl;
        return alloc.allocate(size);
    }
    static void operator delete( void* p, size_t size ) {
        std::cout<<"using overload opeartor delete" <<std::endl;
        return alloc.deallocate(static_cast<char*>(p),size);
    }

    static __gnu_cxx::__pool_alloc<char>  alloc;
    char c;
    double d;
};
__gnu_cxx::__pool_alloc<char> XImpl::alloc;

int main(){
    XImpl * p =new XImpl{};
    std::cout<<p->c<<' '<<p->d<<std::endl;
    delete p;
    return 0;
}
