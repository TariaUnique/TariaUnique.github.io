item31

分析下段代码的调用

namespace A
{
    struct X;
    struct Y;
    void f( int );
    void g( X );
}
namespace B
{
    void f( int i )
    {
        f( i ); // which f()?
    }
    void g( A::X x )
    {
        g( x ); // which g()?
    }
    void h( A::Y y )
    { 
      h(y);
    }
}

f()调用的自己，这会导致无限循环调用。 如果在namespace B中我们通过"using namespace A;" or "using A::f;"，将 A::f(int)引入B中，则这个调用是无法决议的，ambiguous between A::f(int) and B::f(int)。

g的调用是无法决议的。虽然我们没有使用using命令或using声明将A::g(X)引入进来，但是因为B::g(A::X)，这个函数的参数是个A::X 类型，在name lookup时有个Koenig Lookup rule: If you supply a function argument of class type (here x, of type A::X), then to look up the correct function name the compiler considers matching names in the namespace (here A) containing the argument's type. 所以这里的g(x)调用有两个选择，A::g(X) 和 B::g(A::X), 无法决议到哪一个

比如有如下代码段

namespace NS
{
    class T { };
    void f(T);
}
NS::T parm;
int main()
{
    f(parm); // OK, calls NS::f
}

parm是NS::T， f(parm)这个函数调用的name lookup就会应用Koenig Lookup rule,编译器会到NS namespace中查看有没有匹配的函数。 这似乎是打破了namespace的隔离，然而，考虑我们如下替换这段代码

#include <string>
#include <iostream>
std::string parm
int main()
{
    std::cout<<parm;
}

这是一段非常简单并常见的代码，main中的语句调用的是operator<<(ostream& os, const string& str)这个定义在std中的函数。我们在调用这个函数时也没有使用std::限定符，也没有使用using声明将这个函数引用进来，但是编译器还是正确的解析到了对应的operator<<重载，这就是应用了Koenig Lookup rule。 也就是说，Koenig Lookup rule并不是一个特殊设计的名称查找规则，反而这个rule应该是有通用性的，符合某种规则（interface principle）

最后，h的调用也是调用的自己，namespace A中并没有符合的接口，这个调用是明确的，没有二义性。

回顾一下class的定义： A class describes a set of data, along with the functions that operate on that data. Our question is: What functions are "part of " a class, or make up the interface of a class?

那么class的interface是什么？仅仅只有其public member function才是其interface么？ 其实这些public member fucntion也不过就是多了 this 指针，然后他们可以访问到internal data。而如果是friend函数，其参数有class对象，并且也可以访问到internal data。 或者仅仅就是 outside operate function, 比如说string类型的operator<<(), 这难道不能说是接口么？

对于不支持class类型的语言来说，比如c, 某个c struct 的interface，就是其参数中有这个对象的指针，这样就是interface.比如如下代码

struct _iobuf { /*...data goes here...*/ };
typedef struct _iobuf FILE;
FILE* fopen ( const char* filename, const char* mode );
int fclose( FILE* stream );
int fseek ( FILE* stream, long offset, int origin );
long ftell ( FILE* stream );
/* etc. */

fopen, fclose, fseek, ftell就是struct _iobuf的接口。 虽然这样实现的面向对象代码不具有封装性，it relies on client programmers to refrain from fiddling with the data directly。

所以我们有如下的interface principle: For a class X, all functions, including free functions, that both

  • "Mention" X
  • Are "supplied with" X are logically part of X, because they form part of the interface of X. 这里的Are "supplied with" X 通常意味，如果是free function的话，要么是和X定义在同一个namespace中，要么是和X定义在同一个header file中，提供给客户端使用。 而如果是客户端使用X的代码，比如定义了包含X类型参数的函数，这个函数显然并不是X 的interface
class X { /*...*/ };
/*...*/
ostream& operator<<( ostream&, const X& );

Here the Interface Principle's rationale is perfectly clear, because we understand how this particular free function works. If operator<< is "supplied with" X (for example, in the same header and/or namespace), then operator<< is logically part of X because it forms part of the interface of X. That makes sense even though the function is a nonmember, because we know that it's common practice for a class's author to provide operator<< as non member ，because it requires a stream as the left-hand argument. also for operator+ shouldn't be a member in order to allow conversions on the left-hand argument.

由此可见，Koenig Lookup rule引入，就是为了让c++在函数调用解析时，interface的查找能够符合interface principle。

假设name look up 的查找没有Koenig Lookup rule，则如下代码

#include <iostream>
#include <string> // this header declares the function  std::operator<< for strings
int main()
{
  std::string hello = "Hello, world";
  std::cout << hello; // OK: calls std::operator<<
}

Here the compiler has no way to find operator<< without Koenig lookup, because the operator<< we want is a free function that's made known to us only as part of the string package. It would be disgraceful if the programmer were forced to qualify this function name, because then the last line couldn't use the operator naturally. Instead, we would have to write either "std::operator<<( std::cout, hello );" which is exceedingly ugly, or "using std::operator<<;" which is annoying and quickly becomes tedious if there are many operators, or "using namespace std;" which dumps all the names in std into the current namespace and thus eliminates much of the advantage of having namespaces in the first place. If those options send shivers down your spine, you understand why we need Koenig lookup.

While the Interface Principle states that both member and nonmember functions can be logically "part of " a class, it doesn't claim that members and nonmembers are equivalent. For example, member functions automatically have full access to class internals, whereas nonmembers have such access only if they're made friends. Likewise for name lookup, including Koenig lookup, the C++ language deliberately says that a member function is to be considered more strongly related to a class than a nonmember.


namespace A
{
  class X { };
  void f( X );
}

class B // <-- class, not namespace
{
  void f( A::X );
  void g( A::X parm )
  {
    f(parm); // OK: B::f, not ambiguous
  }
};

So in two major ways—access rules and lookup rules—even when a function is "part of " a class according to the Interface Principle, a member is more strongly related to the class than a nonmember.

In summary, I'd like you to take away three thoughts from this miniseries.

  • The Interface Principle: For a class X, all functions, including free functions, that both "mention" X and are "supplied with" X are logically part of X, because they form part of the interface of X.

  • Therefore, both member and nonmember functions can be logically "part of " a class. A member function is still more strongly related to a class than is a nonmember, however.

  • In the Interface Principle, a useful way to interpret "supplied with" is "appears in the same header and/or namespace." If the function appears in the same header as the class, it is "part of " the class in terms of dependencies. If the function appears in the same namespace as the class, it is "part of " the class in terms of object use and name lookup

综上，"supplied with" X有两种情况， appears in the same header but not in the same namespace, appears in the same namespace. 这两个情况有什么不同，看接下来的例子

// Example 2: Will this compile?
//
// In some library header:
namespace N { class C {}; }
int operator+(int i, N::C) { return i+1; }


// A mainline to exercise it:
#include <numeric>
int main()
{
  N::C a[10];
  std::accumulate(a, a+10, 0);
}

答案可能编译通过，也可能编译不通过。看不同的编译器在numeric中放的东西有什么不同，尤其是，如果numeric中声明了operator+的话，肯定是编译不通过的

首先回顾下 name hiding：

// Example 1a: Hiding a name
// from a base class
//
struct B
{
int f( int );
int f( double );
int g( int );
};
struct D : public B
{
private:
int g( std::string, bool );
};
D d;
int i;
d.f(i); // ok, means B::f(int)
d.g(i); // error: g takes 2 args

In short, when we declare a function named g in the derived class D, it automatically hides all functions with the same name in all direct and indirect base classes. It doesn't matter a whit that D::g "obviously" can't be the function that the programmer meant to call (not only does D::g have the wrong signature, but it's private and, therefore, inaccessible ), because B::g is hidden and can't be considered by name lookup.

To see what's really going on, let's look in a little more detail at what the compiler does when it encounters the function call d.g(i). First, it looks in the immediate scope, in this case the scope of class D, and makes a list of all functions it can find that are named g (regardless of whether they're accessible or even take the right number of parameters). Only if it doesn't find any at all does it then continue "outward" into the next enclosing scope and repeat—in this case, the scope of the base class B—until it eventually either runs out of scopes without having found a function with the right name or else finds a scope that contains at least one candidate function. If a scope is found that has one or more candidate functions, the compiler then stops searching and works with the candidates that it's found, performing overload resolutionby parameters and then applying access rules check, maybe followed to decide whether to use virtual table.

我们可以给调用加上限定符，限定编译器在哪个scope查找

// Example 1b: Asking for a name
// from a base class
//
D d;
int i;
d.f(i); // ok, means B::f(int)
d.B::g(i); // ok, asks for B::g(int)

也可以使用using声明将B::g引入到当前scope

// Example 1c: Un-hiding a name
// from a base class
//
struct D : public B
{
using B::g;
private:
int g( std::string, bool );
};

回到之前的问题，很显然，编译器在编译std::accumulate时，std::accumulate looks sth like this

namespace std
{
  template<class Iter, class T>
  inline T accumulate( Iter first, Iter last, T value )
  {
    while( first != last )
    {
      value = value + *first; // 1
      ++first;
    }
    return value;
  }
}

value + *first，编译器在解析这个expression时,需要解析到对应的operator+， 当前我们在std namespace中，所以在std namespace中查找，而编译器当前可见的namespace中的东东取决于头文件中包含的东东，不同编译器其包含的东东是不一样的，比如如果numeric文件include进来了iterator文件，而通常iterator中是包含operator+的，这时候，name lookup结束了，而这个operator+在随后的参数匹配中显然是无法匹配的，会编译不过。而如果头文件中碰巧没有包含operator+,编译器会继续在global中查找，这时候就能找到正确的operator+了。所以，其结果取决于不同的编译器实现。 即使碰巧当前编译通过了，日后如果我们增加了头文件，比如<vector>,又编译不过了

本质上还是global operator+ 很可能被隐藏了，因此，之前的两种解决方法，第一种显式声明，这时候我们要使用accumulate version with predicate,在predicate中显式使用global的operator+,如下

#include <iostream>
#include <numeric>


namespace N { class C {}; }

int operator+(int i, N::C) { return i+1; }


int main()
{
  N::C a[10];
  std::cout<<std::accumulate(a, a+10, 0,[](int i, const N::C& c  ){
    return ::operator+(i,c);
  })<<std::endl;
}

这比较麻烦

而使用using声明是不行的，毕竟我们当前是在std空间中，这个空间我们是不能更改的。

The real solution is to put our operator+() where it has always truly belonged and where it should have been put in the first place: in namespace N.

// Example 2b: Solution
//
// in some library header
namespace N
{
  class C {};
  int operator+(int i, N::C) { return i+1; }
}
// a mainline to exercise it
#include <numeric>
int main()
{
  N::C a[10];
  std::accumulate(a, a+10, 0); // now ok
}

Recall that Koenig lookup says that, in addition to looking in all the usual scopes, the compiler shall also look in the scopes of the function's parameter types to see if it can find a match. N::C is in namespace N, so the compiler looks in namespace N, and happily finds exactly what it needs, no matter how many other operator+()'s happen to be lyng around and cluttering up namespace std;

Guideline : Use namespaces wisely. If you write a class in some namespace N, be sure to put all helper functions and operators into N, too. If you don't, you may discover surprising effects in your code.
