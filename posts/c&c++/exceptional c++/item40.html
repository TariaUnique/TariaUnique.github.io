item40

如下代码，先析构函数，再使用placement new重新构造

void f()
{
    T t(1);
    T& rt = t;
    //--- #1: do something with t or rt ---
    t.~T();
    new (&t) T(2);
    //--- #2: do something with t or rt ---
}// t is destroyed again

首先这段代码可以编译通过，只要我们在in-place destruction(t.~T())和inplace reconstruction(new (&t) T(2))之间不会插入使用t或rt的代码。而且T::operator&()没有被重载，就是返回对象的地址。 满足这两个条件，这段代码在功能上没有什么问题。

但如果T的构造抛出异常，后续可能再次析构t，多次析构可能有问题。

而且原地析构再原地构建是危险的，尤其是在多态的情况下，考虑如下的代码

void T::DestroyAndReconstruct( int i )
{
    this->~T();
    new (this) T(i);
}

class U : public T { /* ... */ };

void f()
{
/*AAA*/ t(1);
/*BBB*/& rt = t;
//--- #1: do something with t or rt ---
t.DestroyAndReconstruct(2);
//--- #2: do something with t or rt ---
}// t is destroyed again

如果/AAA/是T的话，是没什么问题的，不管/BBB/是什么。他可能是T,可能是T的基类 而如果/AAA/是U的话，如果T有虚函数，并且其析构函数是virtual的，那么这里调用的是U的析构函数,然后再该地址处重新创建了T,这样本来的U就被破坏了，后续的访问很有能会core dump. 即使我们使用如下的静态调用

void T::DestroyAndReconstruct( int i )
{
    this->T::~T();
    new (this) T(i);
}

貌似我们只是析构并重新构建了U中的T subobject, 但这还是有问题的，T object作为U object的subobject, 和T object作为一个单独的完整的对象，其构造是不一样的，考虑有虚函数，虚基类的情况，如果T中有虚函数，我们new (this) T(i),重新构造了T对象而不是U对象，那么虚函数表指向了T的虚函数表。如果T有虚基类，我们知道虚基类的构造和析构只能在其most derived 对象中构造和析构，这里的操作就完全将对象数据破坏了。

测试如下

#include <iostream>
using std::cout;
using std::endl;
class T{
public:
    T(int i=0):t(i){}
    virtual ~T(){cout<<"call ~T()\n";}
    virtual void func(){cout<<"call T::func()\n";}
    void DestroyAndReconstruct(int i){
        this->T::~T();
        new (this) T(i);
    }
private:
    int t;
};

class U : public T{
public:
    U(int i):T(i),u(i){}
    ~U(){cout<<"call ~U()\n";}
    void func(){cout<<"call U::func()\n";}


private:
    int u;
};

int main(){
    U t(1);
    T& rt = t;
    rt.func();
    t.DestroyAndReconstruct(2);
    rt.func();
}

output

root@sypc:~/c++# ./a.out
call U::func()
call ~T()
call T::func()
call ~U()
call ~T()

虽然我们通过静态调用只析构了T subobject,但后续的构建修改了我们当前对象的虚函数表，虚函数的调用已经不对了

再考虑如下的拷贝赋值的实现

T& T::operator=( const T& other )
{
    if( this != &other )
    {
        this->~T();
        new (this) T(other);
    }
    return *this;
}

很显然，这样的拷贝赋值操作，目的是为了使拷贝赋值和拷贝构造共用同一份代码。 以拷贝构造来实现拷贝赋值，这确实是有优点的，首先是一致性，其次提高了代码的复用性。 最后，如果T有virtual base class话，尤其是，T是符合virtual base class的菱形继承模型的最底层，那么这种情况下，T的默认拷贝构造对于虚基类的处理是没有问题的，但是T的拷贝赋值，默认情况下，会多次赋值虚基类，这很有可能是会出问题的。参考inside the c++ object chapter 5. 当然，通常虚基类中不应该放数据。而且，如果真是存在虚基类，也就是说T是被用于多态的，很可能需要被继承，那么这种赋值方式就更有问题了。事实上，这种处理方式最主要的可能性问题就出在派生类的处理上。

  • 如果T有虚析构函数，这里的使用方式在派生类的拷贝赋值中会出问题，this->~T();会调用派生类的析构函数，这个和之前的例子是一样的道理。
  • 当然，如果改成this->T::~T();静态调用，一样会有之前的问题，U对象还是会被破坏
  • 这也不是异常安全的。如果T的构造抛出异常了，本来的对象就被破坏了，不能再被使用了。而且后续可能再次析构,多次析构可能有问题

Guideline :Always endeavor to write exception-safe code. Always structure code so that resources are correctly freed and data is in a consistent state even in the presence of exceptions.

  • 这种实现方式，在赋值操作中，对象被析构了一次又被重新构造了一次，如果T是符合RAII原则的，或者T继承自某个符合RAII的基类，也就是其生命周期绑定到某个资源，比如锁资源，或者比如是数据库的事务的开始和结束，那么这样的实现很显然，breaking both client code and the class itself.

之前说过， 以拷贝构造来实现拷贝赋值，这确实是有优点的。如果我们就是需要实现以拷贝构造来实现拷贝赋值函数呢？ using create tmp and swap Provide a Swap() member that is guaranteed not to throw and that simply swaps the guts of this object with another one as an atomic operation, then write the copy assignment operator as follows:

T& T::operator=( const T& other )
{
 T temp( other ); // do all the work off to the side
 Swap( temp ); // then "commit" the work using only
 return *this; // nonthrowing operations
}

最后提一句，如果一个class有引用数据成员，那么它的默认赋值运算符是被delete的，当然我们可以显示提供，只不过要注意引用赋值的语义，是被引用对象的赋值操作。它的默认构造也是被删除的，需要我们自己提供.只有默认拷贝构造是提供的，其引用成员和被拷贝构造的引用指向同一个被引用对象。
